## I. PROJECT CONTEXT

### A. What Is Hotel PMS?

A complete hotel/apartment management system that:

1. ✅ Syncs bookings from OTAs (Airbnb, Booking.com, Agoda, Trip.com) via Channex
2. ✅ Generates smart lock passcodes via TTLock API
3. ✅ Exports immigration reports (XNC NA17 format) for foreign guests
4. ✅ Manages housekeeping tasks and maintenance issues
5. ✅ Scans passports using OCR (MRZ parsing)
6. ✅ Sends notifications via Telegram Bot

### B. Tech Stack

| Layer | Technology |
|-------|------------|
| **Backend** | Python 3.11+, FastAPI, SQLAlchemy 2.0, Pydantic |
| **Database** | PostgreSQL 15 (prod) / SQLite (dev) |
| **Frontend** | Vanilla HTML/CSS/JS, Dark Theme |
| **Deployment** | Docker, Nginx, VPS (Ubuntu) |
| **External APIs** | Channex, TTLock, Telegram |

### C. Service Architecture

```
hotel.khoviet.com (Frontend) :8003
    ↓ REST API
Backend API :8002
    ↓
PostgreSQL :5434
    ↓ External
Channex API → OTAs
TTLock API → Smart Locks
Telegram API → Notifications
XNC Portal → Immigration Reports
```

## III. CRITICAL RULES (MUST FOLLOW)

### Rule 1: No Emoji in Console Output
**Why:** Windows terminal encoding breaks with emoji  
**Action:** Remove/replace ALL emoji from print(), logger, etc.

```python
# ❌ WRONG
print("✅ Database connected successfully")
logger.info("🚀 Starting API server")

# ✅ CORRECT
print("Database connected successfully")
logger.info("Starting API server")
```

### Rule 2: Verify Before Implementing
**Requirement:** Never code based on assumptions.

**Process:**
1. Read error message CAREFULLY (capture exact text)
2. Search codebase for similar patterns
3. Check Python type hints and validation
4. Test understanding on a small example first
5. THEN implement the full solution

### Rule 3: No AI Attribution in Commits
**Forbidden in commit messages:**
- "Used Claude/AntiGravity to generate"
- "AI suggested this implementation"
- "Generated by AI"
- "Co-Authored-By: Claude/AntiGravity"

**Allowed:**
- Technical implementation details
- What changed and why
- Commit type: `feat:`, `fix:`, `docs:`, `test:`

**Format:**
```
type(scope): clear description

- Detail 1
- Detail 2
```

### Rule 4: Single-Purpose Implementation
**Definition:** Implement ONE feature/fix per session, not multiple.

**Why:** Easier to test, debug, rollback

**Example:**
```
Session 1: Add new API endpoint
Session 2: Fix database migration
Session 3: Add frontend page
```

### Rule 5: Test-First Documentation
**Definition:** Never write "Complete ✅" until tests actually pass.

**WRONG Process:**
```
Write code → Create "Feature Complete ✅" doc → Tests fail later
```

**CORRECT Process:**
```
Write code → Run tests → Tests pass → Document "Complete ✅"
```

## IV. CODE STANDARDS

### Python Type Hints (MANDATORY)
```python
# ❌ WRONG - No type hints
def get_booking(booking_id):
    return data

# ✅ CORRECT - Full type hints
def get_booking(booking_id: str) -> Optional[Booking]:
    """Fetch booking by ID.
    
    Args:
        booking_id: UUID of the booking
    
    Returns:
        Booking object or None if not found
    
    Raises:
        HTTPException: If database error
    """
    ...
```

### Error Handling
```python
# ❌ WRONG - Generic exception
try:
    data = service.get_data()
except:
    return None

# ✅ CORRECT - Specific exceptions
try:
    data = service.get_data()
except ValueError as e:
    logger.error(f"Invalid input: {str(e)}")
    raise HTTPException(status_code=400, detail=str(e))
except SQLAlchemyError as e:
    logger.error(f"Database error: {str(e)}")
    raise HTTPException(status_code=500, detail="Database error")
```

### Logging
```python
import logging
logger = logging.getLogger(__name__)

# ❌ WRONG - Using print()
print("Processing booking...")

# ✅ CORRECT - Using logger
logger.info(f"Processing booking {booking_id}")
logger.debug(f"Booking details: {booking}")
logger.warning(f"Passcode generation delayed")
logger.error(f"Failed to sync: {error}")
```

### Adding New Model

1. Define model in `backend/app/models/__init__.py`
2. Create Pydantic schema in `backend/app/schemas/__init__.py`
3. Generate migration: `alembic revision --autogenerate -m "description"`
4. Review migration SQL
5. Apply: `alembic upgrade head`
6. Test with sample data

## VI. SERVICE PATTERNS

### Using Mock vs Real Services

The system automatically uses mock services when real API credentials are not configured:

```python
# backend/app/services/__init__.py
from app.config import settings

if settings.channex_api_key and settings.channex_api_key != "your_channex_api_key":
    from .channex_service import channex_service
else:
    from .mock_services import mock_channex_service as channex_service
```

### Adding New Service

1. Create service file: `backend/app/services/new_service.py`
2. Implement real API integration
3. Add mock version to `mock_services.py`
4. Export from `__init__.py` with auto-fallback
5. Write unit tests for both versions

## X. COMMON TASKS

### Add New Booking Field

1. Add column to `Booking` model
2. Update `BookingCreate`, `BookingResponse` schemas
3. Generate migration: `alembic revision --autogenerate`
4. Apply migration: `alembic upgrade head`
5. Update frontend `app.js` to display/edit field
6. Test end-to-end

### Enable Real Channex Integration

1. Get API key from Channex dashboard
2. Update `.env`: `CHANNEX_API_KEY=real_key`
3. Configure webhook URL in Channex: `https://hotel.khoviet.com/api/v1/webhooks/channex`
4. Restart backend
5. Test booking sync

### Add New Housekeeping Task Type

1. Add to `TASK_TYPES` in `housekeeping.py`
2. Update frontend dropdown in `index.html`
3. Add to mock data in `app.js`
4. Test create/update flow

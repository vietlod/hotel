# Mandatory Rules for ECODATA Development with Claude Code

## Tier 1: Critical Rules (VIOLATING = IMMEDIATE FIX)

### Rule 1.1: No Emoji in Windows Output
- **Why:** Windows console encoding issues cause display corruption
- **Where:** All `print()`, `logger.info()`, print statements
- **Violation:** 🚀, ✅, ❌, 📊, 🔥 (and any other emoji)
- **Action:** Use ASCII alternatives or remove entirely
- **Example:**
  ```python
  # WRONG:  print("✅ Server started 🚀")
  # CORRECT: print("Server started successfully")
  ```

### Rule 1.2: Verify Before Implementing
- **Requirement:** Never code based on assumptions or guesses
- **Action Required:**
  1. Read error message carefully (capture exact text)
  2. Search codebase for similar patterns
  3. Check Python type hints and validation
  4. Test understanding before making changes
- **Violation Examples:**
  - Implementing fix without understanding root cause
  - Adding try-except without handling specific exception
  - Ignoring type hints and validation warnings
- **Recovery:** Revert changes, understand root cause, re-implement correctly

### Rule 1.3: No Claude Code Details in Commits
- **Scope:** Commits messages, comments, documentation
- **Forbidden:**
  - "Used Claude Code to generate this"
  - "Claude AI suggested this implementation"
  - "Generated by AI tool"
  - References to Anthropic, Claude API, or tools
  - "Co-Authored-By: Claude Sonnet 4.5 <noreply@anthropic.com>"
  - Any AI attribution in commit messages
- **Allowed:**
  - Technical implementation details
  - Commit type: `feat:`, `fix:`, `docs:`, `test:`
  - What was changed and why
- **Format:** `type(scope): clear description of change`
- **Example:**
  ```
  # CORRECT: feat(api): add pagination to indicators endpoint
  # WRONG:  feat(api): Claude Code generated indicators endpoint
  # WRONG:  feat(api): add feature\n\nCo-Authored-By: Claude Sonnet 4.5
  ```

### Rule 1.4: Single-Purpose Implementation
- **Definition:** Implement ONE feature/fix per session
- **Why:** Simplifies testing, debugging, and rollback
- **Violation:** Combining multiple unrelated changes
- **Exception:** Related changes to same file (e.g., add endpoint + migration)
- **When Necessary:** Create separate commits for each purpose
- **Example:**
  ```
  Session 1: Add new data source connector
  Session 2: Fix API parameter validation
  Session 3: Add E2E test for the connector
  ```

### Rule 1.5: Test-First Documentation (CRITICAL)

**Definition:** Never create wrap-up documents, status summaries, or "complete" sections until ALL tests pass.

**What NOT to Create (Until Tests Verify Success):**
- "Session #N Complete" summaries
- Status tables showing "✅ Complete"
- Feature lists marked as "Production Ready"
- Deployment success documentation
- Summary wrap-up sections
- Progress reports claiming completion

**What TO Do Instead:**
1. During development: Keep minimal notes (🔄 In Progress)
2. After local tests pass: Document test results
3. After VPS deploys and verifies: Mark ✅ Complete

**Why This Matters:**
- Writing docs before tests = misleading documentation
- Wastes time updating false claims if tests later fail
- Documentation should match reality, not expectations

**Example - WRONG:**
```
Session ends → Create: "Session #42 Complete ✅"
Status: "Feature ready for production"
Later: Tests fail on VPS → Have to rewrite entire document
Waste of time
```

**Example - CORRECT:**
```
Session: Local tests pass → Update: "Session #42 In Progress 🔄"
VPS deploy: All verifications pass → Update: "Session #42 Complete ✅"
Status reflects actual test results
```

## Tier 2: Important Rules (VIOLATING = PERFORMANCE/QUALITY IMPACT)

### Rule 2.1: Update All Documentation
- **Mandatory Files:**
  1. **README.md** - Add feature to overview, update usage section
  2. **CHANGELOG.md** - Add entry with version, date, description
  3. **Code Comments** - Docstrings for all public functions
  4. **CLAUDE.md** - Session notes for future reference
- **When:** Before any commit
- **Verification:** Review each file before `git commit`
- **Length:** CHANGELOG entry should be 2-5 sentences

### Rule 2.2: Testing Before Deployment
- **Unit Tests:** `pytest tests/` (minimum 90% pass rate)
- **E2E Tests:** `pytest tests/e2e/` on Windows (before VPS)
- **API Tests:** Verify endpoints with curl or Postman
- **Manual Testing:** Test feature in browser/API client
- **Deployment Sequence:**
  ```
  Windows: Unit test → E2E test → Manual test → Commit → Push
  VPS: Pull → Test → PM2 restart → Health check → Verify
  ```

### Rule 2.3: Database Migration Discipline
- **For Schema Changes:**
  1. Create migration: `alembic revision --autogenerate -m "description"`
  2. Review migration file (verify SQL is correct)
  3. Test locally: `alembic upgrade head`
  4. Verify with data: Check tables and indexes
  5. Document in CHANGELOG.md
- **Production:** Automatically applied during deployment
- **Rollback:** Keep migration for downgrade if needed

### Rule 2.4: Error Handling Standards
- **All API Routes:** Try-except with specific exception handling
- **All Database Operations:** Handle NULL results and constraints
- **All External API Calls:** Handle network errors + timeouts
- **User Feedback:** Specific error messages (not "Internal Server Error")
- **Logging:** Every error logged with context using logger
- **Example:**
  ```python
  try:
      result = db.query(Indicator).filter(
          Indicator.code == code
      ).first()
      if not result:
          raise HTTPException(status_code=404, detail="Indicator not found")
      return result
  except SQLAlchemyError as e:
      logger.error(f"Database query failed: {str(e)}")
      raise HTTPException(status_code=500, detail="Database error")
  ```

## Tier 3: Best Practices (VIOLATING = SUBOPTIMAL CODE)

### Rule 3.1: Python Type Hints
- **Always Required:** Type hints for all functions
- **No `typing.Any`:** Use specific types instead
- **Type Checking:** Use `mypy` or similar for validation
- **Pydantic Models:** Use for request/response validation
- **Example:**
  ```python
  # WRONG:  def get_data(source):
  # CORRECT: def get_data(source: str) -> List[Dict[str, Any]]:
  ```

### Rule 3.2: Consistent Code Structure
- **Routers:** API endpoint definitions only
- **Services:** Business logic and database operations
- **Models:** SQLAlchemy models and Pydantic schemas
- **Utils:** Reusable functions and helpers
- **Example Structure:**
  ```
  api/
  ├── routes/
  │   └── indicators.py (router)
  ├── services/
  │   └── indicator_service.py (business logic)
  ├── models/
  │   └── indicator.py (database model)
  └── schemas/
      └── indicator_schema.py (Pydantic)
  ```

### Rule 3.3: Consistent Naming Conventions
- **Variables/Functions:** snake_case
- **Classes:** PascalCase
- **Constants:** UPPER_SNAKE_CASE
- **Files:** snake_case (functions), PascalCase (classes)
- **Examples:**
  ```python
  user_count = 5                      # snake_case ✓
  class IndicatorService:             # PascalCase ✓
  MAX_RETRIES = 3                     # UPPER_SNAKE_CASE ✓
  def get_indicators() -> List:       # snake_case ✓
  ```

### Rule 3.4: Git Commit Discipline
- **Frequency:** Commit after each logical change
- **Message Format:**
  ```
  type(scope): description
  
  Optional longer description with context
  ```
- **Types:** feat, fix, docs, style, refactor, test, ci, chore
- **Scope:** Area affected (api, db, etl, frontend, admin)
- **Example:**
  ```
  feat(etl): implement WorldBank data ingestion pipeline
  
  - Add WorldBankConnector class with OAuth2 support
  - Implement data transformation for time-series format
  - Add deduplication logic for duplicate records
  - Test coverage: 95% (24/24 unit tests passing)
  ```

### Rule 3.5: Performance Considerations
- **API Responses:** Implement pagination for large datasets
- **Database Queries:** Add indexes for frequently queried fields
- **Caching:** Redis for frequently accessed data
- **Async Operations:** Use async/await for I/O operations
- **Monitoring:** Log slow queries (>1s execution time)

## Recovery Procedures

### If Violating Tier 1 Rule

1. **Identify the violation** (read error message carefully)
2. **Revert changes:** `git reset --soft HEAD~1` (keeps staged changes)
3. **Understand root cause** (don't repeat fix)
4. **Implement correctly** (follow the rule)
5. **Test thoroughly** (all test suites pass)
6. **Re-commit** with proper message

### If Violating Tier 2 Rule

1. **Identify missing documentation**
2. **Update all required files:**
   - README.md
   - CHANGELOG.md
   - Code docstrings
   - CLAUDE.md
3. **Stage changes:** `git add [files]`
4. **Amend commit:** `git commit --amend`
5. **Verify:** Review final commit before pushing

### If Build Fails on VPS

1. Check error logs: `pm2 logs ecodata | tail -100`
2. Check database: `psql [connection-string] -c "SELECT version();"`
3. Check disk space: `df -h`
4. Check Python version: `python --version` (should be 3.10+)
5. Rollback: `git reset --hard HEAD~1 && pm2 restart ecodata`
